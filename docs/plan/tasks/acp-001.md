# objective

Freeze a **docs-first** ACP adapter contract: `zag --acp` speaks the
**Agent Client Protocol** (the editor↔agent JSON-RPC protocol from the
Claude-Code-SDK ecosystem — Zed, Claude Code, the ACP registry) over local
stdin/stdout pipes, so editors can drive a zag agent exactly as they drive
any ACP agent. The adapter assembles the **existing public coding-agent
surfaces** (Agent / Session / LifecycleObserver / Observer / permission Gate /
control queues / sigint Guard) exactly as the TUI and rpc-v1 hosts assemble
them — **no Core changes, no coding-agent changes, no rpc-v1 changes, no new
package**. It is the "separately gated ACP adapter" of D-012 item 4, sized
for one engineer slice (~2–3 days).

**Binding specification:** [acp.md](../../modules/acp.md)

**Status:** **`implemented`** — product code + process fixture landed
(HEAD after 158542a); see the implementation log at the bottom of this file.

# context

- D-012 item 4: "Zag-native long-lived `rpc-v1` and a separately gated ACP
  adapter". D-012 architecture law: both stay **outside `zag-agent-core`**,
  one-way package graph, Core loop unchanged.
- **rpc-v1-001 is implemented** (HEAD 158542a). The ACP adapter is its
  sibling, not its child: same host surfaces, same fixture style, same
  NDJSON line discipline — but a **different envelope and vocabulary**.
- **Framing fact (verified against the ACP spec, 2026-08-07):** ACP stdio is
  **newline-delimited JSON-RPC 2.0** — one message per `\n`-terminated line,
  UTF-8, no embedded newlines. There is **no Content-Length / LSP-style
  framing** in ACP. The transport shape matches rpc-v1; the envelope
  (`jsonrpc: "2.0"`, string-or-number ids, numeric error codes) and the
  method vocabulary do not. This kills the "framing mismatch" argument for a
  translation layer and makes framing **reuse** (`rpc/framing.zig`) free.
- Method surface extracted from the official sources (2026-08-07):
  - agentclientprotocol.com/protocol/v1 (transports, initialization,
    session-setup, prompt-turn, tool-calls, extensibility);
  - `agent-client-protocol` Rust SDK 0.10.4 + schema 0.11.4 (the crate
    hyper-grok-build builds against; method-name constants, request/response
    shapes, `StopReason`, `PermissionOptionKind`, `ToolKind`,
    `ToolCallStatus`);
  - hyper-grok-build's `x.ai/interject` steer extension (semantic reference
    for mid-run steer).
- **Official ACP v1 agent surface** (baseline = MUST support): `initialize`,
  `authenticate` (if authMethods advertised), `session/new`, `session/prompt`
  (requests); `session/cancel` (notification); agent→client:
  `session/request_permission` (request), `session/update` (notification).
  Optional/stabilized: `session/list`, `session/load`, `session/set_mode`,
  `session/set_config_option`, `session/resume`, `session/close`,
  `session/delete`, `logout`, client `fs/*` + `terminal/*` + elicitation.
- **Not in official ACP** (verified): `initialized`, `ping`, `session/steer`,
  `authentication/getUser` — they are Claude-Code-ecosystem names; the batch
  pins them in the v1 subset as compat/extension methods (see
  [acp.md §6](../../modules/acp.md#6-method-subset-frozen-v1)).
- The zag host surface is exactly the surface rpc-v1 assembled (rpc-v1-001
  implementation log): `Agent.reply`/`requestCancel`, `Session.start` with
  `OpenMode`, `enqueueSteering`/`enqueueFollowUp` (bounded 4 × 4096 B
  queues), `LifecycleObserver`, `observer.Observer`,
  `permissions.Gate.ask`, `sigint.Guard`; `rpc/framing.zig` is protocol-
  agnostic line I/O and is **imported read-only** by the ACP adapter.
- Sibling in flight: `process-supervisor-001` (draft). Supervisor v1 is
  foreground-bounded and hosts agent-*spawned* children; the ACP server is a
  **top-level host** (like TUI/rpc) and spawns no children in v1.
- Zag is on **Zig 0.16** (`std.Io` era): the same constraints as rpc-v1-001.

# dependency decision (frozen)

| Question | Decision |
|----------|----------|
| Does ACP block on process-supervisor-001? | **No.** The ACP server is a top-level long-lived host process (same role as TUI/rpc) and spawns no children in v1 (no `terminal/*`, no MCP servers); its `run_shell` path is the existing synchronous shell-v1 backend, which migrates onto the supervisor independently (orthogonal, zero protocol change). |
| Does ACP sit on top of rpc-v1? | **No — separate adapter** (frozen, module §2). The protocol mismatch is at the envelope/semantics level (JSON-RPC 2.0 envelope + numeric errors + sessionId-correlated surface vs rpc-v1's headless-family envelope + string codes + one-process-one-session), not the transport. A translation layer would either need to refactor the frozen rpc server or run as a second process spawning `zag --rpc` (process-tree ownership — explicitly deferred by D-012 and rpc-v1). The adapter reuses `rpc/framing.zig` read-only, the dual-thread host *pattern*, and the fixture/mock infrastructure, and keeps rpc-v1 frozen. |
| Standalone contract? | **Yes** — third host assembly (TUI → rpc → ACP), own JSON-RPC 2.0 wire types, own session table, own permission request bridge, own shutdown state machine. |
| Shared principles | rpc-v1's host principles adopted: bounded output, truthful terminal (documented exit codes), explicit no-mid-handler-preemption honesty, no OS-sandbox claims, stdout protocol-only. |

# contract summary (draft freeze)

| Topic | Draft freeze |
|-------|--------------|
| Owner | `zag-cli` only (**no new package**); **no** Core/coding-agent/TUI/rpc-v1 changes; `rpc/framing.zig` imported read-only |
| Surface | CLI flag `--acp` (long-lived server mode, stdin/stdout pipes); mutually exclusive with `--rpc` / `--json` / `--json-stream` / `--tui` / `--doctor` / `--verbose` / positional prompt (exit 2, empty stdout) |
| Wire format | **Newline-delimited JSON-RPC 2.0** (ACP transports spec — NOT Content-Length): one object per `\n`-terminated line, `jsonrpc: "2.0"` required, id echoed verbatim, absent id = notification; frame cap **4 MiB** via reused `rpc/framing.zig`, resync at next newline; local pipes only |
| Version | integer `protocolVersion: 1` negotiated once in `initialize` (no per-frame version); breaking changes require a new major version (out of v1) |
| Session model | One server process = one Agent + one Session (startup `-s` / `-c` / ephemeral, rpc-v1 parity); one-row session table with opaque id `sess_1`; `session/new` maps onto the startup session, validates `cwd` == process cwd, rejects mcpServers/prompt/additionalDirectories, **idempotent** |
| Requests (required) | `initialize` (capability negotiation; advertises only `sessionCapabilities.list`, `authMethods: []`), `session/new`, `session/prompt` (single in-flight; busy → `-32001`) |
| Notifications (required) | client→agent `session/cancel` (→ `requestCancel` + pending gate deny); agent→client `session/update` (variants: `agent_message_chunk`, `agent_thought_chunk`, `tool_call`, `tool_call_update`) |
| Agent→client request | `session/request_permission` (ask mode only; options allow_once/allow_always/reject_once/reject_always; outcome → gate decision; cancel/EOF → deny; yolo → none) |
| Optional / extension | `session/list` (advertised; single current row); `session/steer` (extension; queued, ≤ 4096 B, cap 4); `authentication/getUser` (stub: null user); `ping` / `initialized` (compat no-ops, not official ACP) |
| Unknown methods | request → `-32601`; notification → ignored (JSON-RPC rule) |
| Concurrency | Dual-thread host (TUI/rpc pattern): worker runs `Agent.reply`; main thread polls stdin + Guard self-pipe (250 ms); one writer mutex; program-order notifications; prompt response is the last frame of its run |
| Permission | `Gate.ask` bridge emits `session/request_permission` with the adapter's own id; client outcome resolves the condvar; `allow_always` → remember write path; never allow on cancel/shutdown; no gate deadline |
| Lifecycle | Client disconnect (EOF) · first SIGINT/SIGTERM → one graceful sequence: gate deny → cancel → bounded join **30 s** → save (best effort) → exit 0; join expiry → 70; second signal → 130; **no `exit` request** (ACP has none; client owns process lifetime); **no idle timeout** |
| Error model | JSON-RPC codes `-32700` / `-32600` / `-32601` / `-32602` / `-32603`; application codes `-32000` run error, `-32001` busy, `-32002` queue full, `-32003` message too long; run outcomes: `completed→end_turn`, `max_turns→max_turn_requests`, `cancelled→cancelled`, failures → `-32000` error |
| Exit codes | Headless numeric matrix (0/2/30/31/32/33/40/50–55/60/70/130) with applicability table; startup failures → stderr diagnostic + exit code (no stdout bytes — no JSON-RPC error channel pre-initialize) |
| Redaction | Every string through the session redactor; explicit exceptions: `cwd` (echoed from the client's own request — ACP mandates absolute paths; zero new disclosure) and the opaque `sessionId` |
| Budgets | Frame 4 MiB; prompt text 1 MiB; steer 4096 B; permission fields 64 KiB; tool body 64 KiB; join 30 s |
| Fixtures | `acp_process_fixture.zig` (fake editor over pipes/PTY, real `zag --acp` binary, headless mock + slow mock): ~25 classes incl. mode matrix, handshake, session/new mapping, prompt round-trip + busy, cancel, steer, permission flows, list/getUser/ping, JSON-RPC errors, framing resync, redaction, PTY + SIGINT gates, disconnect, startup exit codes, ownership scan; std **and** curl backends |
| Maturity | **no row raise**; no OS sandbox; no network/auth |
| Orthogonal | TUI / Theme / vaxis; process-supervisor; LSP; rpc-v1 (frozen); MCP / E2; headless-v1; Session/Trace schemas |

# non-goals

- Full ACP/SDK compatibility and parity (D-009); ACP v2 draft; ACP registry advertisement
- `session/load` / `session/resume` / `session/close` / `session/delete` / `session/fork` / `session/set_mode` / `session/set_config_option` / `session/set_model` / `logout`; `authenticate` flow (not advertised)
- Client-side surfaces: `fs/*` / `terminal/*` / elicitation / `usage_update` / plan·state updates / user-message replay
- Initial prompt in `session/new`; per-run `maxTurns` override; `allowInterruptions` enforcement (advisory)
- Multi-session concurrency; session-store scanning in `session/list`
- Multi-client; network transports (streamable HTTP / WebSocket); MCP servers; additional workspace roots
- Authentication flows beyond the `authentication/getUser` stub
- Network transport, sockets, auth tokens (local pipe, same-user trust only — rpc-v1 §3 rationale)
- Prompt queueing; background jobs; idle timeout; server-side run deadlines
- In-flight Tool/shell preemption claims (same honesty as everywhere: cancel at boundaries)
- TUI integration; rpc-v1 / headless-v1 / Session v1 / Trace v1 changes; Core or coding-agent ports
- New Zig package; maturity raise; OS sandbox; process-tree ownership


# implementation log (acp-001)

Landed on top of 158542a (rpc-v1-001 HEAD), implementing the frozen contract
as written:

- `packages/zag-cli/src/acp/protocol.zig` — JSON-RPC 2.0 envelope
  parse/serialize, frozen v1 method subset, error codes, budgets,
  capability constants, session/update variants, permission wire shapes.
  Unit-tested without IO.
- `packages/zag-cli/src/acp/server.zig` — dual-thread host (rpc/server.zig
  pattern): read loop + guard self-pipe poll, dispatch, worker
  (`Agent.reply` on the flattened prompt), one-row session table
  (`sess_1`), Gate.ask condvar bridge emitting `session/request_permission`
  with the adapter's own id, `allow_always` remember store (server-owned,
  `allow_once` suppresses the gate's automatic remember), cwd-canonicalized
  `session/new` validation, run outcome mapping (§11.3), graceful shutdown
  (EOF/first signal → gate deny → cancel → 30 s join → save → exit 0;
  join expiry → 70). Imports `rpc/framing.zig` READ-ONLY; `acp/framing.zig`
  deliberately absent.
- `packages/zag-cli/src/acp_entry.zig` — `--acp` wiring; startup failures
  emit NO stdout bytes (stderr + headless exit code, acp.md §10.4).
- `packages/zag-cli/src/cli.zig` — `--acp` flag, mutual-exclusion matrix
  (exit 2, empty stdout), stderr help, startup exit-code mapping (30/31/40),
  acp host branch.
- `packages/zag-cli/src/headless_mock_server.zig` — additive extensions
  (default behavior unchanged): `--tool-path`, `--tool-call-count`,
  `--tool-call-every`, `--log-file`, per-connection unique tool-call ids.
- `packages/zag-cli/src/acp_process_fixture.zig` + root `build.zig`
  `acp-process-fixture` step (wired into `test`) — fake editor over
  pipes/PTY against the real `zag --acp` binary, std + curl backends.
- `docs/plan/tasks/acp-001.md` — status → `implemented`.

Fixture status at landing: **32/33 gates green** (mode matrix, help,
handshake, protocol errors, session/new mapping + validation, prompt
round-trip, content blocks, busy, cancel, steer, control caps, permission
allow/deny, cancel-pending-gate, session/list, extensions, JSON-RPC errors,
framing resync, redaction, PTY protocol-only + EOF, PTY signals,
disconnect, startup failure, ownership). **gate15 (permission remember) is
RED**: with `--tool-call-every 2`, the second prompt's run receives a
well-formed tool-call SSE response (verified standalone; mock alive per
`--log-file`), but the agent returns `-32000 provider error` before the
tool executes — an interaction between the coding-agent loop's streaming
tool-call parsing and a second tool call in the same session, outside the
adapter (the adapter truthfully surfaces the run failure per §11.3; the
no-re-ask property is not yet proven by this gate). Root-cause follow-up
belongs to a coding-agent-focused change; the adapter code and the other
permission gates are unaffected.
